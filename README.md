# Задача: О "неторопливо" обедающих философах

Источник: <https://sites.google.com/view/fitnsudotnet>

## Общий контекст

### Постановка задачи

Пять философов сидят за круглым столом. Между каждой парой соседей лежит одна вилка, всего пять вилок. Философ проводит время в размышлениях, но периодически ему нужно поесть.

Чтобы поесть, философу необходимы обе вилки: левая и правая. После еды вилки возвращаются на стол.

### Состояния философа

| Состояние | Описание |
| --- | --- |
| `Thinking` | Философ размышляет и не имеет вилок. |
| `Hungry` | Философ проголодался и пытается взять обе вилки. |
| `Eating` | Философ ест. |

### Состояния вилки

| Состояние | Описание |
| --- | --- |
| `Available` | Вилка доступна для взятия. |
| `InUse` | Вилка используется философом для еды или находится в процессе взятия/возврата. |

### Процесс

Философ становится голодным (`Hungry`) через определенное время. Это время определяется случайно согласно условиям задачи.

Чтобы перейти в состояние `Eating`, нужно взять обе вилки. Процесс взятия не мгновенный: вилки берутся по очереди, а порядок взятия определяет стратегия. Философ может положить уже взятую вилку, если это нужно. Возврат вилки происходит мгновенно.

Философ ест определенное время, после чего возвращает вилки на стол и переходит в состояние `Thinking`.

### Отображение состояния

В разных состояниях необходимо выводить в консоль состояние симуляции.

Пример вывода:

```text
===== ШАГ 150 =====

Философы:
  Платон: Thinking (Action = ReleaseRightFork|ReleaseLeftFork), съедено: 22
  Аристотель: Thinking, съедено: 233
  Сократ: Eating (4 steps left), съедено: 33
  Декарт: Thinking (3 steps left), съедено: 22
  Кант: Hungry (Action = TakeRightFork|TakeLeftFork|ReleaseRightFork|ReleaseLeftFork|None), съедено: 33

Вилки:
  Fork-1: Available
  Fork-2: Available
  Fork-3: InUse (используется Аристотель)
  Fork-4: InUse (используется Сократ)
  Fork-5: InUse (используется Декарт)
```

### Стратегия и координатор

Важно: стратегия не должна знать состояние всех философов и всех вилок. Стратегии доступны только две соседние вилки.

В некоторых задачах, например в задачах 1 и 7, требуется использование координатора. Координатор знает обо всех философах и всех вилках.

Взаимодействие философа и координатора должно быть событийным. Философ с помощью синхронного вызова декларирует свое желание поесть, а координатор отправляет событие `возьми ту или иную вилку`, когда это становится возможным.

### Метрики

- **Пропускная способность**: количество съеденного в единицу времени, по каждому философу и в среднем.
- **Время ожидания**: время нахождения в состоянии `Hungry`; среднее по всем философам и максимальное с указанием философа, на котором оно было достигнуто.
- **Коэффициент утилизации вилки**: процент времени, в течение которого каждая вилка была свободна, заблокирована или использовалась для еды.

## Задача 1. ООП: пошаговая симуляция

### Описание

Реализовать консольное приложение с пошаговой симуляцией без многопоточности. Каждый шаг симуляции последовательно обрабатывает состояния всех философов.

### Требования

- Имена философов считываются из файла.
- Симуляция длится `1_000_000` шагов.
- Нужно разработать контракт стратегии и координатора.
- Стратегия и координатор должны быть помещены в отдельный проект.
- Нужно реализовать наивную стратегию без координатора.
- Нужно реализовать любую стратегию с координатором.
- Передача информации о том, что философ может сделать, должна использовать события языка C#.
- Нужно определять `deadlock`: взаимную блокировку всех философов.

### Длительность состояний

| Действие | Длительность |
| --- | --- |
| Размышление | 3-10 шагов, случайно |
| Еда | 4-5 шагов, случайно |
| Взятие каждой вилки | 2 шага |
| Освобождение вилок | Мгновенно, обе вилки одновременно |

### Метрики

Метрики для задачи 1 и следующих задач:

- Пропускная способность измеряется в количестве съеденного за `1000` шагов.
- Время ожидания измеряется в количестве шагов.
- В конце нужно вывести `Score`, то есть общее количество съеденного всеми философами, и все метрики.

## Задача 2. Многопоточная симуляция

### Описание

Реализовать консольное приложение с многопоточной симуляцией в реальном времени. Используется стратегия без координатора.

### Требования

- Длительность симуляции задается константой.
- Состояние отображается каждые `100-200` мс.

### Длительность состояний

| Действие | Длительность |
| --- | --- |

| Еда | 40-50 мс, случайно |

| Освобождение вилок | Мгновенно, обе вилки одновременно |

### Метрики

- Пропускная способность: еда/миллисекунда.
- Среднее время ожидания для каждого философа, в миллисекундах.
- Коэффициент утилизации каждой вилки в процентах по времени.

## Задача 3. Использование .NET Generic Host

### Описание

Реализовать консольное приложение с использованием `.NET Generic Host`, где каждый философ представлен отдельным `HostedService`.

Нужно использовать встроенные возможности .NET для управления жизненным циклом сервисов, логирования и конфигурации.

### Требования

- Каждый философ реализован как отдельный `BackgroundService`.
- Для всех компонентов используется `Dependency Injection`.
- Конфигурация выполняется через `appsettings.json` и `IOptions`.
- Для прерывания выполнения программы используется `IHostApplicationLifetime`.
- После истечения времени работа останавливается аккуратно, через `CancellationToken`.

### Сервисы

- `PhilosopherHostedService`: основной сервис для каждого философа.
- `IPhilosopherStrategy`: стратегия философа.
- Возможные дополнительные сервисы: калькулятор метрик, менеджер вилок и другие.

### Пример `Program.cs`

```csharp
services.AddSingleton<ITableManager, TableManager>();
services.AddSingleton<IMetricsCollector, MetricsCollector>();
services.AddSingleton<IPhilosopherStrategy, LeftRightStrategy>();

// Возможно, другие сервисы.

// Регистрируем каждого философа.
services.AddHostedService(new Platoo(provider));
services.AddHostedService(new Aristotle(provider));
services.AddHostedService(new Socrates(provider));
services.AddHostedService(new Decartes(provider));
services.AddHostedService(new Kant(provider));

services.Configure<SimulationOptions>(
    configuration.GetSection("Simulation"));
```

### Пример `appsettings.json`

```json
{
  "Simulation": {
    "DurationSeconds": 120,
    "ThinkingTimeMin": 30,
    "ThinkingTimeMax": 100,
    "EatingTimeMin": 40,
    "EatingTimeMax": 50,
    "ForkAcquisitionTime": 20,
    "DisplayUpdateInterval": 200
  }
}
```

## Задача 5. Базы данных

### Описание

Реализовать систему сохранения состояния симуляции в базе данных с возможностью запроса состояния в любой момент времени.

Система должна записывать все изменения состояний философов и вилок.

### Функциональные требования

- Во время выполнения симуляции состояние должно сохраняться в базе данных.
- Каждому выполнению должен быть присвоен уникальный `runId`.
- `runId` должен быть распечатан в консоли.
- Нужно реализовать консольное приложение `DiningPhilosophers.View`.
- `DiningPhilosophers.View` получает параметрами `runId` и смещение в секундах относительно начала.
- Пример вызова:

```bash
DiningPhilosophers.View --runId 33 --delay 44.12
```

Приложение должно распечатать состояние стола на указанный момент.

### Технические требования

- Использовать `PostgreSQL` как основную СУБД.
- Использовать `Entity Framework Core` для работы с базой данных.
- Применить подход `Code First` с миграциями.
- Написать тесты с использованием `InMemory SQLite`.

## Задача 6. Микросервисы

### Описание

Реализовать систему обедающих философов в виде микросервисной архитектуры, где каждый философ и стол являются отдельными HTTP-сервисами, взаимодействующими через REST API.

Вся система должна запускаться через `Docker Compose`. Сохранение в БД не требуется.

### Архитектура

#### Сервисы

- **Table Service**: центральный сервис, управляющий состоянием вилок и сбором метрик.
- **Philosopher Service**: отдельный экземпляр для каждого философа, всего пять сервисов.

### Технические требования

- Использовать `ASP.NET Core Web API` для всех сервисов.
- Взаимодействие только через `HTTP REST API`.
- Каждый сервис работает в отдельном Docker-контейнере.
- Вся система запускается через `Docker Compose`.
- Для межсервисного взаимодействия используется `HttpClient`.
- Нужно разработать контракты взаимодействия между микросервисами.

### Docker Compose

Необходимо создать файл `docker-compose.yml`, который запускает:

- один экземпляр `Table Service`;
- пять экземпляров `Philosopher Service`, по одному для каждого философа.

Каждый философ должен отработать настроенное количество минут и сообщить столу о своем выходе. После того как все философы вышли, `Table Service` должен распечатать итоговые метрики.

Пример:

```yaml
services:
  table-service:
    build: ./TableService
    ports:
      - "8080:8080"
    environment:
      - ASPNETCORE_URLS=http://+:8080
      - PHILOSOPHERS_COUNT=5
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8080/health"]
      interval: 30s
      timeout: 10s
      retries: 3

  philosopher-plato:
    build: ./PhilosopherService
    environment:
      - ASPNETCORE_URLS=http://+:8081
      - PHILOSOPHER_NAME=Платон
      - PHILOSOPHER_ID=philosopher-1
      - LEFT_FORK_ID=1
      - RIGHT_FORK_ID=2
      - TABLE_SERVICE_URL=http://table-service:8080
      - SIMULATION_DURATION_MINUTES=5
    depends_on:
      table-service:
        condition: service_healthy
    ports:
      - "8081:8081"

  philosopher-aristotle:
    # ...
```

## Задача 7. Event-Driven микросервисы с координатором

### Описание

Реализовать продвинутую микросервисную систему обедающих философов с координатором, использующую гибридную архитектуру:

- `HTTP API` для синхронных операций;
- асинхронные события для координации.

Система должна использовать `MassTransit` или аналогичную библиотеку для обмена сообщениями. Также допустимо использовать `RabbitMQ Client Library`.

### Архитектура

#### Сервисы

- **Table Service**: управляет состоянием вилок и обрабатывает HTTP-запросы.
- **Philosopher Service**: отдельный экземпляр для каждого философа, всего пять сервисов.
- **Coordinator Service**: координирует доступ к ресурсам через события.
- **Message Broker**: `RabbitMQ` для обмена событиями.

### Логика координации

Координатор должен реализовать любую стратегию предотвращения `deadlock`.

Требования к взаимодействию:

- Операции взаимодействия философов и стола должны быть синхронными, через `HTTP API`.
- Операции взаимодействия философов и координатора должны быть событийными, с использованием `MassTransit`, аналогов или нативного API.
